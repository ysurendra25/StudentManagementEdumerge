# AI Usage Report — Smart Attendance Management

**AI TOOL USED:** Sarvam AI assistant (Claude-based); headless Chromium for
screenshot verification; AI-assisted scaffolding of the Spring Boot /
React project structure.

**WHAT I ASKED AI TO DO:**

1. Product design first: understand the assignment brief (the Edumerge
   5-option PDF), choose Assignment 1, define users/roles/workflows/
   permissions for a ~5,000-student college, and produce five key product
   mockups (faculty marking, HOD dashboard, defaulters report, correction
   workflow, student view) before any code.
2. Build a first working prototype (an earlier Flask version), then — because
   Spring Boot + React is the stack I can defend in an interview — a **full
   rewrite as Spring Boot 3 (Java 21) + React 18 (Vite) + H2**: JPA entities,
   repositories, controllers, session auth with role checks, the correction
   workflow, the defaulters/recovery engine, the React SPA, and the
   deterministic seeder.
3. Test and validate: a scripted end-to-end suite (23 checks — marking,
   re-mark block, proxy block, future-date block, correction cycle, defaulter
   math, CSV export, notifications, audit, role guards) run against a freshly
   seeded database, plus screenshot-rendered visual checks of every screen.

**PROMPT THAT WAS MOST USEFUL:**

> "I don't know Flask well enough to defend it in the interview — I've built
> projects with Spring Boot and React, so rebuild the whole assignment in
> Spring Boot + React with the same product logic, keep the Flask version as
> a reference, and re-run the full end-to-end test suite from a fresh
> database so nothing is accepted on trust."

**CODE GENERATED BY AI: What part?**

Most of the code: the Spring Boot backend (entities, repositories with
native aggregate queries, controllers, `AuthInterceptor`, `SpaForwardFilter`,
`SeedRunner`), the React frontend (all pages, router, styling), the seed
data generator, the smoke-test script, and drafts of the README and this
report. The product decisions (roles, correction policy, recovery math,
what counts as an edge case) were decided in discussion and reviewed by me.

**CODE I MODIFIED: What part?**

- Fixed three entity→table mismatches (`Department`, `Student`, `Correction`
  defaulted to singular table names while the native SQL used plural) which
  crashed seeding and the dashboard.
- Fixed the derived query method names on the composite-key repository
  (`findBySessionIdAndStudentId`, not `findByIdSessionId…`).
- Fixed the auth interceptor: `/api/auth/**` was described as open in the
  comment but actually fell through to the "must be logged in" catch-all,
  breaking demo login — added the explicit exemption.
- Fixed two `*/` sequences inside a Javadoc comment that terminated it early
  and broke compilation.
- Fixed a JSX compile error (raw `<` inside text) in the Dashboard KPI cards.
- Removed dead scaffolding code the AI left in early drafts before committing.

**AI OUTPUT THAT WAS WRONG:**

1. The three table-name mismatches above ("Table CORRECTIONS not found" at
   startup; dashboard 500 "Table DEPARTMENTS not found").
2. Wrong Spring Data method derivation (`No property 'idSessionId' found`).
3. The interceptor auth-hole for `/api/auth/**` (returned 401 on login —
   caught by the very first API test).
4. Javadoc and JSX comment errors above (compilation failures).
5. A first draft of `SeedRunner` passed the wrong argument count to a helper
   (compile error) and generated duplicate usernames for same-surname
   faculty — the latter fixed by the username-uniquifying helper I asked for.

**HOW I IDENTIFIED THE PROBLEM:**

- Reading the actual startup/compile logs and tracebacks — every one of the
  errors above was surfaced by running the app or build, not by eyeballing
  the code.
- The scripted end-to-end suite: login as each role, mark a session, attempt
  illegal actions (re-mark, future date, another faculty's slot, wrong-role
  endpoints), raise and decide corrections, export the CSV, then assert on
  HTTP status, response bodies, and the database effects (e.g. the roster
  really changed after an approval).
- Re-running the whole suite from a **freshly seeded database** after every
  fix, so no fix was accepted on trust and no earlier state leaked into
  later runs.
- Rendering each React page headlessly and inspecting screenshots for blank
  screens or broken layout.

**HOW I FIXED IT:**

Each fix was made at the model level rather than papering over symptoms:
explicit `@Table` names matching the SQL, correct derived-query naming, an
explicit auth-exemption branch, comment syntax fixes, and a re-run of the
entire 23-check suite from a clean seed after every change. Final state:
**23/23 passing from a fresh database**, all screens visually verified.
